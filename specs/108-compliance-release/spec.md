# 规格：合规与发布（108-compliance-release）
> 工程：`dsh-desktop-ark`
> 状态：应用标识、设备形态、单实例、权限声明、签名注入、构建模式 **implemented**；双发行线、ACL/合规材料、包体与可复现门禁、路径无关构建 **planned**
> 来源：`docs/000-工程规划.md` §12.1–§12.4、§7.5、§11.1（P4）、§14（D3/D4/D10）；`specs/overall-spec.md` §3.7；`specs/overall-plan.md` §6

## 1. 模块概述
**目的**：让应用能装、能审、能发：标识与版本可追溯、权限最小且与实现一一对应、签名材料不入库、同一份代码产出"标准"与"无 JIT 兜底"两条发行线，并具备上架所需的合规材料。

**问题**：
- 内嵌运行时依赖 JIT，2in1/平板上的可写代码内存属受限权限；审核不通过就没有产品，因此必须有兜底发行线。
- 权限清单容易"先声明再说"：未实现的能力也声明权限，是最常见也最致命的上架驳回原因。
- 签名材料一旦入库或写进构建配置，等于把发布凭据长期暴露。
- 版本号规则若不机械化，两条发行线很快会互相覆盖或回退。
- 构建脚本绑定某台机器的盘符与 Windows 专属命令，等于"只有我能发版"。

**范围**：
- 范围内：应用标识与版本规则、设备形态、单实例、权限清单与授权面、签名材料来源与注入优先级、构建模式与发行线、包体预算、二进制不入库、产物可追溯、合规材料清单。
- 范围外：应用内权限使用体验（`104`/`106`）、诊断内容（`107`）、载荷装配细节（`102`）、运行时投放细节（构建前置脚本）、商店文案与截图运营。

**状态分解**：

| 组成 | 状态 |
|---|---|
| 应用标识（包名、厂商、图标、名称） | implemented |

| 设备形态（仅 2in1 / tablet） | implemented |
| 单实例与长时任务模式 | implemented |
| 权限声明与自定义声明 | implemented（但与 §12.1 不一致，见 plan F5/F6） |
| 签名材料注入（环境变量 / 本地忽略文件 / 无材料产出未签名包） | implemented |
| 调试与正式构建模式 | implemented |
| 双发行线（标准 / 无 JIT） | **planned** |
| 包体预算门禁 | **planned** |

## 2. 用户故事
- 作为维护者，我能在一台干净机器上按文档产出可安装包，不依赖某个盘符或某个人的桌面环境。
- 作为维护者，我能在不持有任何密钥的情况下完成编译验证。
- 作为发布负责人，我能确定"这次要发的是哪条线、版本号是多少、与上次相比是否递增"。
- 作为合规负责人，我能把每个声明的权限对应到一段真实实现，找不到对应就删掉。
- 作为审核方看到的材料，能说明为什么需要受限权限、没有它时产品如何降级。

## 3. 功能需求
### 3.1 标识与版本
- **FR-108-001**：应用标识（包名、厂商、应用名、图标）MUST 稳定；修改包名 MUST 视为新产品，MUST NOT 原地升级。
- **FR-108-002**：设备形态 MUST 仅包含 2in1 与 tablet；MUST NOT 声明 phone。
- **FR-108-003**：应用 MUST 单实例运行；重复启动 MUST 复用已有实例。
- **FR-108-004**：版本号 MUST 按"主 * 10000 + 次 * 100 + 修订"计算，且 MUST 单调递增；版本名 MUST 与版本号同步。
- **FR-108-005**：两条发行线 MUST 各自维护版本号序列，MUST NOT 互相覆盖或回退。
- **FR-108-006**：版本相关事实（版本号、版本名、构建模式、载荷幂等键）MUST 出现在产物清单或诊断事实中，便于追溯。

### 3.2 权限与授权面
- **FR-108-007**：权限清单 MUST 与规划中的权限基线逐项一致（双向：声明项 ⊆ 基线，基线中的必需项 ⊆ 声明项）。
- **FR-108-008**：未实现的能力 MUST NOT 声明其权限；已声明的每个权限 MUST 能指向一段真实使用它的代码。
- **FR-108-009**：受限权限 MUST 在"申请清单"与"自定义声明"两处成对出现。
- **FR-108-010**：每个受限权限与用户授权权限 MUST 携带申请理由与使用场景。
- **FR-108-011**：权限申请 MUST 按需触发，MUST NOT 在冷启动时批量弹窗（与 `106` 一致）。
- **FR-108-012**：受限权限未被授权面包含时，安装 MUST 直接失败；MUST NOT 在运行期静默降级成"看起来能用"。
- **FR-108-013**：装机失败的已知错误码 MUST 被登记在合规文档中，供排障引用。

### 3.3 签名与构建
- **FR-108-014**：签名材料 MUST NOT 入库；仓库 MUST NOT 出现证书、私钥、签名配置本地文件。
- **FR-108-015**：构建 MUST 支持两种签名来源：环境变量、被忽略的本地配置文件；两者优先级 MUST 确定且可预测。
- **FR-108-016**：没有任何签名材料时，构建 MUST 产出未签名包并给出明确告警，MUST NOT 直接失败（编译验证不依赖密钥）。
- **FR-108-017**：签名配置不合法（模式非法、必填字段缺失、文件不可解析）MUST 立即失败并指出原因。
- **FR-108-018**：调试签名与正式签名 MUST 分离；正式包 MUST 只通过应用市场分发。
- **FR-108-019**：构建脚本 MUST 与具体盘符和 Windows 专属命令解耦，MUST 在文档声明的受支持环境下可重跑。
- **FR-108-020**：二进制（运行时库、HAR、载荷归档）MUST NOT 入库，MUST 由脚本投放并在缺失时给出可执行提示。

### 3.4 发行线与合规
- **FR-108-021**：发行线 MUST 由构建剖面区分，共享同一包结构；差异 MUST 仅限 JIT 开关与构建参数。
- **FR-108-022**：无 JIT 线 MUST 关闭 WASM 能力，并 MUST 在文档与界面登记"性能降级"。
- **FR-108-023**：包体 MUST ≤ 200 MB（未压缩）；超限 MUST 优先裁剪市场预置与文档类资源。
- **FR-108-024**：AI 合规材料（算法备案、模型登记、安全评估）与隐私声明 MUST 在发版前就绪，并 MUST 与开发并行推进。
- **FR-108-025**：诊断与日志类数据 MUST NOT 静默上报；导出 MUST 只在用户主动操作时发生。
- **FR-108-026**：上架检查 MUST 覆盖：权限最小化、隐私声明、日志脱敏、无明文凭据、包体、双线可安装。

## 5. 验收场景
### AC-108-01 权限与基线一致
- **Given** 应用清单与应用代码
- **When** 逐项对照权限基线与权限使用点
- **Then** 双向一致；不存在"声明但无使用"与"使用但未声明"（TC-108-001）

### AC-108-02 无密钥可编译
- **Given** 环境中没有签名材料
- **When** 执行构建
- **Then** 构建成功并产出未签名包，日志中有明确告警（TC-108-002）

### AC-108-03 双线可区分
- **Given** 两条发行线的构建参数
- **When** 分别产出包体
- **Then** 两条线的产物可区分，版本号各自递增，无 JIT 线在界面标注降级（TC-108-003）

### AC-108-04 包体预算
- **Given** 完整载荷与运行时
- **When** 统计未压缩包体
- **Then** ≤ 200 MB；超限时裁剪顺序符合规格（TC-108-004）

### AC-108-05 仓库无密钥
- **Given** 仓库文件清单
- **When** 检索证书、私钥、签名配置
- **Then** 结果为空（TC-108-005）

### AC-108-06 装机前置失败可见
- **Given** 授权面缺少受限权限
- **When** 安装应用
- **Then** 安装失败并返回已登记的错误码；MUST NOT 装成"能启动但功能静默缺失"

### AC-108-07 版本单调
- **Given** 上一次发布的版本号
- **When** 产出新包
- **Then** 同一发行线的版本号严格递增，且版本名与版本号一致

## 6. 非功能需求
| 类别 | 要求 |
|---|---|
| 可复现 | 同输入同产物；二进制不入库；脚本幂等 |
| 安全 | 密钥与凭据不入库、不进日志；正式签名与调试签名分离 |
| 体积 | 未压缩包体 ≤ 200 MB；超限有裁剪顺序 |
| 合规 | 权限最小化、理由与场景齐备、材料可提交 |
| 失败可见 | 签名/权限/SDK 缺失一律显式失败或显式告警，不静默降级 |

---
## 7. 假设与约束
- 构建与签名工具链由外部命令行工具提供，版本按技术选型锁定；本模块不引入第二套构建系统。
- 受限权限需要单独审核，审核周期以工作日计；因此兜底发行线 MUST 与主线并行准备。
- 应用市场是正式包的唯一分发渠道；侧载仅限调试签名。
- 内嵌运行时的体积是包体主要构成，压缩原生库为必选策略。
