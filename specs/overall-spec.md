# 整体规格（overall-spec.md）

> 工程：`dsh-desktop-ark`
> 版本：v0.1（`000-scaffold`）
> 本文件**不含实现细节**（不出现框架名、文件路径、API 名）。实现见 `overall-plan.md` 与各模块 `plan.md`。
> 需求语言遵循 RFC 2119：MUST / SHOULD / MAY。

---

## 1. 系统目的与用户

**目的**：在 HarmonyOS / OpenHarmony 的 2in1 与 tablet 设备上，提供 DeepSeek Harness（dsh）的桌面级客户端：同一个 Web 界面、同一套 agent 能力、同一份会话数据，不依赖 Electron，不重写界面。

**目标用户**

| 角色 | 诉求 |
|---|---|
| 终端用户 | 在鸿蒙电脑/平板上像桌面应用一样使用 dsh：对话、工具调用、工作区文件、插件市场 |
| 开发者 | 用上游同一套前端与插件机制；升级上游不需要重做适配 |
| 维护者 | 平台差异集中、可审计、可回归；每个降级都有登记 |

---

## 2. 核心能力（用户故事）

- 作为用户，我打开应用后**不需要任何配置**就能看到 dsh 主界面并新建会话。
- 作为用户，我的会话、草稿、滚动位置在**重启应用后仍然存在**。
- 作为用户，我可以让 agent **执行命令**、读写工作区文件、搜索内容。
- 作为用户，我可以在**沙箱 / 桌面 / 文档 / 下载**四个位置中选择工作区，且不会误入其它目录。
- 作为用户，我可以在应用内**浏览并安装插件**（不预装第三方插件）。
- 作为用户，当我离开应用时，**审批请求与任务完成**会以系统通知告知我。
- 作为用户，当运行时启动失败时，我能看到**可复制的原因**并一键重启应用。
- 作为维护者，我能用一条命令判断构建是否可复现、上游契约是否变化。

## 3. 功能需求

### 3.1 应用生命周期（FR-APP）

- **FR-APP-001**：应用 MUST 单实例运行；重复启动 MUST 复用已有实例。
- **FR-APP-002**：应用 MUST 支持 2in1 与 tablet 两种设备形态；MUST NOT 声明 phone。
- **FR-APP-003**：用户退出时，应用 MUST 在 2 秒内完成收尾并退出；MUST NOT 拦截系统终止。
- **FR-APP-004**：应用 MUST 在冷启动时创建运行期目录（载荷、日志、home、工作区、桥），重复启动 MUST 幂等。

### 3.2 运行时（FR-RUN）

- **FR-RUN-001**：应用 MUST 在自身进程内启动一个真正的 Node.js 运行时；MUST NOT 以子进程方式启动随包运行时。
- **FR-RUN-002**：运行时启动 MUST 在 60 秒内达到可服务状态；超时 MUST 进入失败态并给出日志尾。
- **FR-RUN-003**：服务 MUST 只监听回环地址，端口 MUST 由系统分配（不固定）。
- **FR-RUN-004**：运行时 MUST NOT 在崩溃后自动重启；失败态 MUST 引导用户重启应用。
- **FR-RUN-005**：页面进入服务 MUST 依赖服务自身签发的一次性凭据；应用外壳 MUST NOT 参与鉴权。

### 3.3 界面（FR-UI）

- **FR-UI-001**：主界面 MUST 渲染上游 Web 前端，且 MUST NOT 修改其业务代码。
- **FR-UI-002**：启动过程中 MUST 显示可理解的阶段提示；失败时 MUST 显示阶段、原因、日志尾与「重启应用」。
- **FR-UI-003**：应用 MUST 阻止页面导航到非本机服务地址；外部链接 MUST 交给系统浏览器/系统能力。
- **FR-UI-004**：页面 MUST 支持本地存储（否则首屏不可用）；MUST 在加载完成后清理启动页历史，避免返回键卡死。

### 3.4 宿主能力（FR-CAP）

- **FR-CAP-001**：宿主能力 MUST 以结构化数据请求/响应，且 MUST NOT 抛异常给调用方。
- **FR-CAP-002**：未注册的能力 MUST 返回明确错误码；未实现的能力 MUST 返回「未实现」与提示，MUST NOT 返回伪成功。
- **FR-CAP-003**：目录选择 MUST 限定在四个主目录内，MUST 提供授权预检与申请入口。
- **FR-CAP-004**：通知 MUST 覆盖审批请求、任务失败、任务完成三类事件。
- **FR-CAP-005**：外部打开 MUST 只放行工作区内文件与 https 链接。

### 3.5 数据与工作区（FR-DATA）

- **FR-DATA-001**：会话数据 MUST 持久化在应用沙箱内，卸载即清除。
- **FR-DATA-002**：工作区 MUST 位于四个主目录之内；用户目录 MUST 固定解析并做存在性检查，缺失时 MUST NOT 回退到其它目录。
- **FR-DATA-003**：用户目录不可用（未授权/不存在）时，界面 MUST 显示不可用与重试入口。
- **FR-DATA-004**：随包载荷 MUST 由运行时自身解包并校验版本；重复启动 MUST 跳过已解包版本。
- **FR-DATA-005**：升级后 MUST 保留上一版本载荷以便回滚；回滚 MUST 通过重启应用生效。

### 3.6 诊断（FR-DIAG）

- **FR-DIAG-001**：应用 MUST 提供四类可取证信息：运行时日志、业务日志、系统日志、崩溃记录。
- **FR-DIAG-002**：诊断信息 MUST NOT 包含凭据/token。
- **FR-DIAG-003**：调试构建 MUST 提供本机事实端点；正式构建 MUST NOT 暴露该端点。

### 3.7 发布（FR-REL）

- **FR-REL-001**：发布 MUST 提供标准线与无 JIT 兜底线两条构建。
- **FR-REL-002**：受限权限 MUST 在安装前获得授权面支持；缺失 MUST 在装机阶段失败而非运行时静默降级。
- **FR-REL-003**：版本号 MUST 单调递增；两条发行线各自递增。

## 4. 非功能需求

| 类别 | 要求 |
|---|---|
| 启动性能 | 冷启动到首屏 ≤ 10 s（已解包载荷）；首次启动（含解包）≤ 60 s |
| 包体 | HAP ≤ 200 MB（未压缩） |
| 稳定性 | 单个插件/工具异常 MUST NOT 终止应用进程 |
| 可观测 | 任一失败 MUST 能在 `app.log` 找到阶段与原因 |
| 隐私 | 不静默上报；诊断仅在用户主动复制时导出并脱敏 |
| 可访问性 | 跟随系统深浅色；关键错误提供可读文本而非仅图标 |
| 国际化 | 首期中文；错误文案与能力名保持英文标识符 |

---

## 5. 系统边界

**范围内**：对话与工具调用、命令执行、文件读写/搜索、会话持久化与搜索、附件图片、四主目录工作区、通知、插件市场与运行时安装、诊断、双发行构建。

**范围外**：手机形态、PTY 真终端、进程级沙箱、git 工具、多窗口/多实例、自建 Node 运行时、跨设备同步、账号体系改造。

**依赖边界**：上游 dsh 的 profile/bundle/seam 是唯一适配面；运行时的启动/观测/桥由 `@fellow99/node-bridge`（ohpm 中心仓包）提供，引擎由 `@fellow99/node-runtime` 随包分发；平台事实以真机实测为准。
