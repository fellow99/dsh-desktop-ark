## 2. 本轮修掉的阻塞缺陷（按发生顺序）

1. **`ohos-node-bridge` 的 HAR 与运行时**：HAR 重建（502,310 B）；运行时七项 ELF 门禁通过并按 `runtime.lock.json` 校验 SHA-256 后投放。
2. **载荷缺上游 `lib/` 产物**：`deepseek-ai/dsh` 工作树里 10 个包（`working-directory`、`tool-working-directory`、`web-deepseek-api`、`subagent-*`、`ui-secret-mask` 等）没有 `lib/`，装配后 profile 行 `failed to import`。处理：跑全量 `build:lib:host` → `build:lib:client` → `build:web` 后重装配，未激活行降为 **0**。
3. **`node-addon-require-builtin` 无 OHOS 目标**（首轮真机失败点）：app-boot 的 profile 解析必须读 `internal/modules/*`，而该原生 addon 只有 darwin/linux/win32 预编译 → `No usable native binding found for …-openharmony-arm64`。处理：新增垫片 **S6**（`payload/shims/require-builtin.js`）在装配期替换该包，运行时加 `--expose-internals`。
4. **`payload/host.js` 拼 URL 用了不存在的 `webServer.protocol`** → `Invalid URL`，Host 永远到不了 `ready`。处理：按上游 `localWebUrl` 口径固定 `http://127.0.0.1:<port>`，并对端口做正整数校验。
5. **ArkWeb 输入即黑屏**（真机必现）：`RenderMode.ASYNC_RENDER`（默认）下 Web 是独立图形 surface 节点，系统输入法窗口出现/关闭后该 surface 脱离合成树——截图整片黑、DOM 仍正常（CDP 截图可见页面完好）。处理：改用 `RenderMode.SYNC_RENDER`（画布节点与系统组件一起合成）后键入恢复正常；另关闭 `enableAutoFill`（会拉起系统 AutoFillAbility 窗口）。
6. **工作区选择器无客户端面**：上游 `directory-picker-auto` 会动态挂载 backend+surface 一对，被我们的 bundle 禁用后无人挂载 surface，「选择工作区」点击无反应。处理：在 `packages/bundle-ohos/cordis.patch.yml` 显式钉住 `@deepseek-ai/dsh-client-ui-directory-picker-browse`。
7. **工作区选择器 host 面挂起**：`workspace-picker` 原本通过 `isolate()` + 动态 `import('@deepseek-ai/dsh-host-directory-picker-browse')` 委派 browse 原语，在 OHOS 宿主上该 import 使 RPC 永久挂起（客户端停在「加载中…」，服务端无错误无响应）。处理：本包自实现 `list`/`createDirectory`（只用 `node:fs`），围栏与 canonical 归一化同时作用于两个原语；smoke 用例同步改为断言真实创建与列举。
8. **调试通道**：`debug` 构建开启 `webview.WebviewController.setWebDebuggingAccess(true)`，配合 `hdc fport tcp:<port> localabstract:webview_devtools_remote_<pid>` 可用 CDP（本轮定位黑屏、校验页面状态、驱动表单均依赖它）。

## 3. 关键实测事实（供后续复用）

- 净启耗时：HAP 装机后首启 60–75 s（解包 15,124 文件约 13 s）；命中 marker 的冷启约 3 s 到 `ready`。
- HAP：82 MB（含 `libnode.so` 120.9 MiB）→ 载荷 40.1 MB gz 后 **86 MB**；`entry-default-signed.hap` 由 hvigor 用 `signing.debug.local.json` 签名。
- 设备沙箱（`/data/storage/el2/base/haps/entry/files`）：`hdc shell` **可读** `payload/`、`workspace/`、`dsh-home/`，**不可写**（uid 不符）；`dsh-home/.credentials.yaml` 为 `0600`，shell 读不到（符合预期）。
- `snapshot_display` 在 ASYNC_RENDER 下会拍到黑屏（见缺陷 5）；改 SYNC_RENDER 后拍照恢复正常，可直接作为 UI 判据。
- `uitest dumpLayout` 在本机可用（可拿到 Web 组件 bounds）；ArkWeb 内部元素仍需 CDP 或坐标点击。
- 系统 `snapshot_display` 与 CDP `Page.captureScreenshot` 可互为交叉验证：前者验"用户看到的"，后者验"Chromium 渲染的"。


## 3.1 2026-10-20 追加轮：文档 / 下载 Tab 的针对性测试（已闭环）

起点：`atm perm -r -b org.fellow99.dsh.DshDesktopArk` 复位成「装完未授权」（两项均 `status -1 / flag 0`），
装机 `sha12=dd2fd2cc3ee5`，全部操作走真实 UI（`uitest uiInput click` + `uitest dumpLayout` 取证）。

| 步骤 | 结果 | 判据 |
|---|---|---|
| 打开选择器 → 点「文档」 | ✅ 授权门（「未获得该目录的访问权限」+ 请求权限 / 刷新），**不列目录、`atm` 未变** | `dumpLayout` 文本 + `atm dump` 前后一致 |
| 点「请求权限」 | ✅ 系统弹窗「允许"DSH Desktop"访问你的"文档"文件夹？」 | `dumpLayout` 读到 不允许 / 允许 |
| 点「允许」 | ✅ **自动列出** `DevEcoStudioProjects` / `JianyingPro` / `pi203-documents`（无需点刷新） | `dumpLayout` 三个 📁 行；`atm` → `grantStatus 0` |
| 「下载」同样流程 | ✅ 弹窗「…你的"下载"文件夹？」→ 允许后**自动列出 7 项** | `dumpLayout` 7 个 📁；`atm` → `grantStatus 0` |
| 点「不允许」 | ✅ 留在授权门，显示「平台没有给出授权结果（authResults 为空）…」 | `atm` 保持 `-1` |

本轮同时定位并修掉两个**平台行为导致**的缺陷（细节见 `ACL配置.md` §5 / §6）：

1. **`requestPermissionsFromUser` 的返回值不可信**：本设备上这两项权限**授予与拒绝都返回 `authResults: []`**；
   而 `checkAccessTokenSync` 又有**已知假阴性**（`atm` 为 0、目录可读，它仍报未授予）。
   ⇒ 判定基准换成**真实 `readdir`**（`probeAccess`），权限 API 只用于归因。
2. **授权生效滞后几百毫秒** ⇒ 申请后必须**短轮询**探测（`probeAccessSettled`，8×350 ms），
   否则界面会停在「未授权」，用户得手点一次「刷新」。

另记一条**装机命令坑**：本机 `hdc install -r <hap>` 必须带 `-t <目标序列号>`，否则只回
`[Fail]ExecuteCommand need connect-key?`（`install` 不像 `shell` 会自动选中唯一目标）。
